## Q9: what the server's Python sees and does with bots

### 1. With only bots, the round never runs, so no scoring, ticket or stats code runs

- Python handlers registered without `alwaysCall` run only while the game is `Playing` **and** the
  begin-round state is Running (3) (`PythonHost.cpp:806-813`, `:68`). The same gate applies to
  `bf2.Timer`s and triggers (`:2418-2421`, `:2503-2506`).
- The begin-round state leaves "waiting" only when `getNumberOfAliveHumanPlayers() >=
  numPlayersNeededToStart` (`GameLogic/ServerGameLogic.cpp:446-451`). That count is connected,
  non-AI players only (`Scene/Object/PlayerManager.cpp:887-897`), so bots never count.
- **`sv.numPlayersNeededToStart 0` does not help in this tree.** `ServerSettings::getNumPlayersNeededToStart`
  returns a hard-coded 2 before its real body (`Game/GameServer/ServerSettings.cpp:333-342`, a
  `[CHOSEN, not recovered]` release-build floor). With the file set to 0, RCON
  `exec sv.numPlayersNeededToStart` answers `2`. The contract's "0 also starts the timer and
  tickets" (Q7 row, "How these bots differ", "Testing") is therefore wrong for `540fa88`.
- Observed (tracer, run B3): for every bot event only the `alwaysCall` handlers ran (mm_webadmin,
  mm_autobalance, mm_tk_punish, mm_kicker). `gpm_cq.onPlayerKilledCQ` / `onPlayerDeathCQ`,
  `scoringCommon.onPlayerKilled` and the `stats.py` per-round hooks were registered through the
  wrapper on `Playing` and **never called**. After a bot killed a bot, `bf2cc pl` showed 0 kills,
  0 deaths and score 0 for both, no `playerScore` line was sent, and the end-of-round line read
  `gameStateEndGame | CH | 999 | US | 999` (no ticket lost).
- With two humans present the round runs, and then the same code treats bots like humans: there is
  no `isAIPlayer` test in `scoringCommon.py`, `gpm_cq.py` or the scoring paths of `stats.py`; a bot
  gets a stats record with profile id 0 (`python/bf2/stats/stats.py:449-476`, a new record on every
  connect). Rank, medals and snapshot are imported only when `getIsAIGame()` is 0
  (`python/bf2/__init__.py:93-112`), which it is; the image ships `rank.py` but no `medals.py` or
  `snapshot.py`, and `rank.py` asks GameSpy for stats only for profile ids above 2000
  (`rank.py:51-53`). **Not exercised at runtime**: it needs two human clients.

### 3. A crash raises in mm_webadmin, so crashes are never reported

When a heli crashes with the bot in it, the engine fires `PlayerKilled(victim, None, None, (), None)`.
`mm_webadmin.onPlayerKilled` evaluates `attacker.index` first and raises (tracer, run B1-B3):

```
PlayerKilled handler mm_webadmin.onPlayerKilled raised:
  File "admin/modules/mm_webadmin.py", line 583, in onPlayerKilled
    if victim.index == attacker.index:
AttributeError: 'NoneType' object has no attribute 'index'
```

The exception is swallowed (`PythonHost.cpp:815-819`), so BF2WebAdmin gets only `vehicleDestroyed`,
`exitVehicle` and `playerDeath`. This is not bot-specific (any death without an attacker, the
existing `# TODO: crashing in plane/heli doesn't show`), and the roadkill branch below it
(`:587-591`) is unreachable for the same reason. It matters for bots because 2v2 rounds are decided
by crashes. It is the **only** handler exception seen in all runs.

### 4. Team: the PlayerConnect handlers run before the module sets the team

- `createInputPlayer` fires Python `PlayerConnect` (event 14) inside the engine call
  (`GameServer.cpp:542-545`), before it returns to the module, which only then calls `setTeam`
  (`src/Module.cpp:519`).
- `mm_autobalance.onPlayerConnect` (`admin/modules/mm_autobalance.py:113-144`) puts the new,
  not-yet-alive player on the smaller team; for the first bot that is team 2 (`team2` is -1 after
  removing the newcomer, so `p.setTeam(2)`). `mm_webadmin.onPlayerConnect` (`mm_webadmin.py:552-556`)
  reports that team.
- The module's `setTeam(team, false)` and Python's `p.setTeam` both change the team without a
  `PlayerChangeTeams` event: none was recorded and the tracer saw no `PlayerChangeTeams` call in any
  run. So BF2WebAdmin shows every bot on team 2 until a `wa connect` replays the player list
  (`sendReconnectMessage`, `mm_webadmin.py:134-142`, which reads the live team). `bf2cc pl` and
  TickState show the right team.

## Q5: is "collective held" a safe watchdog neutral?

**No.** Holding collective with cyclic and pedals at 0 is safe only in a hover. In three of the
five states it crashes the Z10 within 12 s.

### Method

`serverext_client.py --scenario q5` (log `q5-full.log`, every tick in `q5-full.csv`). One bot flies
the team-1 `ahe_z10` on `dalian_2_v_2` with a client-side autopilot (altitude, attitude and heading
hold; signs as measured in module-v0), sets up a state, then **stops sending `SetInput`** for that
bot and records every TickState for 20 s. The module repeats the last input for 6 ticks, then its
watchdog sets cyclic and pedals to 0 and holds collective (`src/Module.cpp:763-775`). The bot then
re-mounts (respawn and re-enter if needed) and climbs back to a hover for the next state.

| State | Set-up at the cut | Last input (collective) |
|---|---|---|
| hover | 62 m above the pad, still | 0.39 |
| climb | full collective, attitude held level, vy +10.9 m/s, 81 m up | 1.00 |
| descent | collective fixed below hover, vy −7.0 m/s, 103 m up | −0.08 |
| forward | 8.6° nose down, 28.8 m/s level, 78 m up | 0.89 |
| banked turn | 31.6° left bank, 25 m/s, 78 m up | 0.87 |

The descent collective was lower than intended (0.12 below a hover collective the client misread
as 0.04; fixed in the client since by averaging), so that descent is a steep one, −7 m/s.

The same five states were then repeated with the client **emulating** two candidate neutrals after
the cut (`NeutralEmulator`: the last input for 6 ticks, then the law below, sent each tick):

- **level**: cyclic pitch `−0.05·pitch − 0.05·pitch_rate`, cyclic roll `+0.05·roll + 0.05·roll_rate`
  (degrees, degrees/s), pedals `−0.03·yaw_rate`, collective held.
- **hover**: level, plus collective as a PI on vertical speed starting from the held value:
  `c_i −= 0.03·vy·dt`, collective `= c_i − 0.03·vy`. It needs no hover-collective value.

One run of each (15 trials). Health 0.75 in the later trials is damage from the hard landing in
`descent/level`; the bot kept that heli.

### Results

Altitude change, worst attitude and speed at 10 s after the cut (20 s in brackets where it adds
something). "LOST" = the bot died (crash).

| State | Module neutral (collective held) | level (emulated) | hover (emulated) |
|---|---|---|---|
| hover | +4.6 m, pitch ≤ 3.2°, 0.7 m/s (+8.2 m at 20 s) | +3.0 m, 6.5 m/s forward drift | −6.5 m, 0.7 m/s (−11.1 m, 0.0 m/s) |
| climb | **LOST at 10.4 s**: the nose rises steadily (−4.7° → −26° at 5 s → −61° at 8 s), it climbs 49 m, then falls backwards and flips (roll 178° at 10 s), 40 m below the cut point | climbs on: +99 m (+177 m at 20 s), attitude ≤ 5° | +21.9 m, then holds; 1.2 m/s |
| descent | **LOST at 11.6 s**: keeps sinking at 7-12 m/s, nose drops to +22°, 22 m/s into the ground | sinks at 7 m/s, attitude ≤ 3.5°; lands hard at 14 s (health 1.00 → 0.75), survives | −11.6 m, then holds (−16.7 m at 20 s) |
| forward 29 m/s | survives 10 s: +13 m, slows to 22.7 m/s, nose rising (+8.6° → +2.9°); by 20 s +76 m, nose −20°, flying backwards at 15 m/s: the climb case again | +49 m (+116 m at 20 s), 12.7 m/s | +14.4 m, 9.4 m/s (+15.7 m, 8.3 m/s) |
| banked turn 32° | **LOST at 10.3 s**: the bank decays only slowly (32° → 19° at 5 s) while the nose drops to 23°: a descending spiral, 94° of turn, 49 m/s, −78 m by 10 s | roll 31.5° → 1.1° in 3 s, then +47 m, 12 m/s | roll 31.5° → 0.9° in 3 s, +13.7 m, 9.5 m/s |

What the data says about the Z10:

- **Zero cyclic holds the current attitude**; it does not level the heli. In the hover cut, pitch
  stayed at −3.2° for 20 s, and in the turn cut the bank took 10 s to decay from 32° to 3°. Whatever
  attitude the sidecar left the heli in mostly persists.
- **Collective away from hover makes the nose move.** High collective pitches the nose up (climb:
  about −5°/s by the end, the cruise case after 10 s), low collective pitches it down (descent).
  With cyclic at 0 nothing stops that, so a held non-hover collective diverges.
- The hover collective is about 0.39 here, and a 29 m/s level cruise needs about 0.89. So "held"
  is far from hover in every state except a hover.

### Answer and proposal (not implemented)

"Collective held, cyclic and pedals 0" is safe only from a hover. It crashed the heli from a
full-collective climb (10.4 s), a steep descent (11.6 s) and a 32° banked turn (10.3 s), and turned
a 29 m/s cruise into the climb case within 20 s. A sidecar that dies mid-manoeuvre usually loses
the heli.

Proposed neutral for a bot in a vehicle, in the module (no wire change; the protocol text under
"Watchdog" changes):

1. **Level the attitude**: cyclic from a P-D on pitch and roll towards 0, pedals damp the yaw rate.
   On its own (`level`), this saved the turn and the descent (a hard but survivable landing at
   7 m/s) but not the climb: a held 1.0 collective climbed 177 m in 20 s, and a held low collective
   still lands hard.
2. **Hold vertical speed at 0**: collective as a PI on vertical speed, starting from the held value.
   With 1 and 2 (`hover`), all five states survived. Altitude settled within −17 to +22 m of the
   cut point, attitude within 5° after 3 s, and speed bled to under 10 m/s. It needs no per-vehicle
   hover collective; the integrator finds it.

Complexity: everything it needs is already computed per tick for TickState (attitude from the
transform, velocity from the physics node). It needs about 30 lines in `neutralise`/`updateBots`,
per-bot state (the previous attitude for rates, the collective integrator), and the signs already
measured (pitch + = nose down, roll + = bank right, pedals + = yaw right). The gains were tried only
on the Z10, once per state; the AH-1Z and other helis are untested. Nothing was tried on planes or ground
vehicles, so the proposal is for helicopters only; anything else keeps today's neutral. A further step, horizontal
velocity damping (tilt against the drift, i.e. a real hover hold), would stop the 6-10 m/s drift
that `level` and `hover` leave; it was not tried.

On foot nothing changes (every axis 0 is already right). On disconnect the bots are destroyed
after the watchdog period, so the neutral matters for 6 ticks there; with a longer `watchdogTicks`
it matters for longer.

## Proposed contract changes (for the coordinator; protocol.md not edited)

1. **Q7 / "How these bots differ" / "Testing"**: `sv.numPlayersNeededToStart 0` has no effect at
   `540fa88` (`ServerSettings.cpp:336-342` returns 2). With bots only, the round never reaches
   Running: no round timer, no tickets, no scoring, no `playerScore`, no stats, no Running-gated
   Python timers or triggers. Two connected humans are needed, or an OpenBF2 decision about that
   `[CHOSEN]` floor. Q7's "0 also starts the timer and tickets" should be withdrawn.
2. **Q5, Watchdog**: replace "collective held" with the level-attitude plus vertical-speed-hold
   neutral above, for helicopters only, as a module change without a wire change.
3. **Team changes**: an admin (`bf2cc switchplayer`, `!sw`, BF2WebAdmin `team`) or ModManager can
   change a bot's team. Today such a bot never respawns (endless `SpawnBlocked`) and `EnterVehicle`
   checks the old team. Proposal: the module compares `getTeam()` with its cached team every tick
   and, on a change, re-resolves the home and target groups for the new team and resets the
   fallback. TickState's team is authoritative; the sidecar must handle a team change.
4. **`BotRemoved` reason 3**: no admin action removes a bot. Kick and ban are no-ops for an
   unconnected player, though clients still see the kick notice. Say so in the contract; removing a
   bot is the sidecar's job, or later the admin channel's.
5. **Banning a bot through ModManager** writes a permanent `N/A` address ban (`mm_bans.xml`).
   BF2WebAdmin should not offer kick or ban for bots (`ai=1`), or the admin channel should map them
   to `RemoveBot`.
6. **mm_webadmin and BF2WebAdmin** (for `admin-channel-draft.md` and the BF2WebAdmin backend): bots
   arrive with team 2 whatever their team, profile 0, address `N/A`, hash `None`, ping 0, and no
   `playerChangeTeam` follows. Crashes produce no `playerKilled` (`mm_webadmin.py:583`). The native
   admin channel should send the team after the module has set it and report attacker-less deaths.
7. **Man-down**: TickState's alive flag stays set for `sv.manDownTime` (2 s) after a kill. A
   man-down bit in the entry flags would let the sidecar react at once (v2 candidate).
8. Q9 can be marked answered with this file. Q5 is answered for the Z10; the neutral is a proposal.
